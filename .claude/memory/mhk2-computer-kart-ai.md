Traced from the disassembly on 2026-11-19 (user asked: "check if in 50/100/150 ccm they are slower than the player") and measured the same day.

**Answer: yes, by design.** A computer kart never gets full throttle while it is level with the player, in any class.

**The throttle** (AI controller fn 0x43A4E0, one per computer kart, `esi` = controller, `[esi+10h]` = its car, output throttle at `[esi+14h]`, brake `[esi+18h]`, steering `[esi+1Ch]`):
- `r` = distance of this kart ahead of the player in units (fn 0x437830: progress difference times lap length; negative = behind; in two-player races the nearer player).
- `C` = base factor of the class, `A`/`B` = distance and factor when ahead, `D`/`E` = when behind:

| Class (table index) | C (level) | ahead: B at A units | behind: E at D units |
| --- | --- | --- | --- |
| 50 cc (0) | 0.7 | 0.5 at 300 | 0.8 at 300 |
| 100 cc (1) | 0.8 | 0.6 at 200 | 0.9 at 200 |
| 150 cc (2) | 0.9 | 0.7 at 100 | 1.0 at 100 |

  Linear from C at r = 0 to B (ahead) or E (behind), constant beyond A / D.
- Times the kart's strength: `[3 classes][6]` = 1.0, 0.95, 0.9, 0.8, 0.7, 0.6, the same in every class. The slot of each kart is gp+0x218 + kart*4, dealt out at random each race (0x412457..0x412583: `rand(7 - humans)`), so in one-player races the six karts get the six values in a random order.
- Use (0x43AAF5..0x43AB44): when the controller does not want to brake and the race phase is not 3/4, throttle = 1.0 below speed 10 (0x596D3C, so the launch is at full throttle), else the factor above. So the best kart in 150 cc reaches full throttle only when 100 units behind; the weakest 50 cc kart drives at 0.6 * 0.7 = 0.42 when level.

**The table object**: singleton at [0x5E852C] (getter 0x401940), 0x9C bytes, built in 0x41A260 with immediate constants. **Correction 2026-11-19: these are only defaults.** The object is `LevelSettings`; each track's `objects.txt` overwrites them (serializer fn 0x419EF0, sections `AI 50cc` / `AI 100cc` / `AI 150cc` and `Target ranking ...` = the strengths; the serializer's offsets are 4 lower than the ones below, not checked why). Per track C (normal factor) for 50 / 100 / 150 cc: 1: 0.7 / 0.85 / 0.8, 2: 0.7 / 0.8 / 0.9, 3: 0.7 / 0.9 / 0.9, 4: 0.7 / 0.9 / 0.8, 5: 0.8 / 0.9 / 0.95, 6: 0.8 / 0.9 / 0.95, 7: 0.9 / 0.9 / 0.95, 8: 0.9 / 0.95 / 0.95. The measurements below were all on track 1. More in [[mhk2-tracks-and-championships]]. Defaults: +0x14 A[3] (300, 200, 100), +0x20 B[3] (0.5, 0.6, 0.7), +0x2C C[3] (0.7, 0.8, 0.9), +0x38 D[3] (300, 200, 100), +0x44 E[3] (0.8, 0.9, 1.0), +0x50 a float 0 used at 0x40647C / 0x406EE2 (unknown), +0x54 strength [3][6]. Class index read at 0x43A501 and 0x43A5B8 (`mov edi,[eax+10h]` = gp+0x10), clamped to 2 by the patch at 0x43A504 / 0x43A5BB, so 200 cc, 250 cc and the tuning class all use the 150 cc row.

**How the controller brakes** (traced 2026-11-22, user: "AI has trouble to keep on track on some places with 250 ccm, e.g. start curve of Egypt"). The AI controller object: vtable 0x598C94, constructor 0x43ABE0, stored in the car at car+0x1F4 (setter 0x42C240), its car at +10h; outputs throttle +14h, brake +18h, steering +1Ch. The update 0x43A4E0 looks ahead to two points at distances speed / [+ACh] + [+A4h] and speed / [+B0h] + [+A8h] (fn 0x43A150; constructor values 200, 0.1, 200, 0.5), takes a curvature there and a corner speed sqrt([+B4h] / curvature) (250000), times 0.8 * ground friction + 0.2, capped by car+33Ch; above it, it brakes ((speed - ...) / [+B8h], 5). These constants are the same in every class, so in 250 cc the karts look ahead too little for their braking distance (linear in speed, while braking distance grows with its square).
Measured on Egypt (track 3), 60 s, one race each (`runs\v19\aiexp`, `ai_race.py --ai-look / --ai-corner / --ai-steer`, `ai_offtrack.py`): resets of the six karts / mean speed / seconds nearly still: 150 cc 1 / 31.7 / 5.2; 250 cc 11 / 39.2 / 14.9; look-ahead x1.5 8 / 33.2 / 37.9; x2 9 / 35.0 / 23.6; corner speed x0.7 11 / 37.6 / 26.9; steering angle x1.5 (written to car+18Ch mid-race; not checked that the physics takes it then) 7 / 39.2 / 15.3; look x1.5 and corner x0.8 5 / 36.9 / 15.8. **Why 200 FPS made them crash more: the power-ups** (traced 2026-11-22, user: "Yes, trace it"). The steering is frame-time based (the car's steering step gets the frame time from fn 0x4305F0's argument). The stuck check in the controller (+8Ch timer, +90h distance summed per 1 s window, +98h, state +9Ch: 0 driving, 1 backing out for 1 s if it moved less than 1 unit, 2 trying again for 2 s, then it asks for a respawn via [car+5Ch]+8) is skipped while the car's state car+29Ch is 10, 15, 20 or 24, and the karts that stood still at 200 FPS were in 24, 20 and 15: hit by power-ups, speed exactly 0, until the game reset them. (Correction 2026-11-27: car+29Ch is the driver's animation; 15 is "drop" and 20 "respawn", see [[mhk2-tracks-and-championships]]; which animation a power-up hit plays is not traced.) The cause: at 0x43A5E5 a kart that holds an item (car+270h >= 0) fires it when rand(800) == 0 (fn 0x4922D0 = rand() % n), once per controller update = per frame. Measured with `race_recorder.py` / `item_rate.py`: 60 FPS 12 uses per minute, an item held 10.6 s; 200 FPS 21 to 23 per minute, held 2.5 to 3.8 s, 12.7 s frozen after hits in one race.
Fix (patch 1.9, `ai_item_chance`, always on): rand(800 / 60 / frame time), the frame time being the update's argument ([esp+88h] at the call; the callee 0x50A800 pops 10h with only three pushes, which is why later code reads it at [esp+8Ch]). Exactly 800 at 60 FPS. After the fix at 200 FPS: 12 to 13 uses per minute on Moorhuhn X, 6 to 7 on Egypt, held 8.5 to 16 s. Resets per minute / seconds standing still (200 FPS, switch on, 2 races; `runs\v19\itemfix`): Moorhuhn X 250 cc 7.5 / 17.9 -> 7.0 / 14.5, Tempo 200 % 14.0 / 22.5 -> 6.5 / 9.6; Egypt 250 cc 8.5 / 24.6 -> 5.5 / 18.4, Tempo 200 % 11.5 / 17.9 -> 11.5 / 27.0 (unchanged); Moorhuhn X 250 cc at 60 FPS 5.0 in that batch (2.7 earlier).
