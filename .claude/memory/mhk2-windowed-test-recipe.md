MHK2-XXL.exe normally starts in exclusive 800x600 fullscreen, which would change the user's display resolution. For testing, run a *test-only copy* in a sandbox folder (never inside `input`) with these tweaks (worked on 2026-11-17/18, Windows 11, 2560x1440 @150 % scaling):

- exe byte at VA 0x0046F8B7: `01` -> `00` (fullscreen flag off -> framed dev window path); 0x46F94A `6A 20` -> `6A 0B` and 0x46F94E `6A 21` -> `6A 0C` make the client area big enough.
- settings.dat: resolution index (object +0x18, file offset 0x14) = 0 (640x480). 800x600 fails with "Camera::Create: can't create the frame-raster". A run WITHOUT settings.dat uses the constructor defaults (800x600, both volumes 100 %): patch those too (0x4030A5 `89 46 08 89 46 0C` -> `89 5E 08 89 5E 0C`, 0x4030C9 imm 1 -> 0) or it crashes / plays music.
- settings.dat music/sfx volume (file offsets 4 and 8) = 0 to keep it silent.
- `vmode=0` on the command line does NOT work (same raster error).

The user works on the PC while tests run (told me on 2026-11-18 that keyboard/focus tests disturbed them), so test without keyboard and without focus:

- Focus at start: what takes the foreground is not the game window but invisible developer dialogs ("Messages", "Watches", "Control Panel", "Create Game Element"; class #32770) that the game creates while it starts. A new process may take the foreground once, and creating such a dialog does it; the keyboard focus then sits on a window nobody sees. The test builds (`prep_fps.py`, `no_activation`) therefore make the library's `CDialog::Create(template, parent)` at 0x57D3F6 return FALSE at once (`33 C0 C2 08 00`), so none of these dialogs exists; the game runs fine without them. In addition the frame window is created with WS_DISABLED (0x46F8F2 `68 00 80 CF 00` -> `.. CF 08`), all 17 dialog templates in the resources get WS_DISABLED, and RenderWare's window calls get SWP_NOACTIVATE (0x53302A, 0x533DEA, 0x534B50 `6A 06` -> `6A 16`; 0x533E85 `6A 26` -> `6A 36`) and SW_SHOWNOACTIVATE (0x53140E `6A 09` -> `6A 04`). Measured with `focus_probe.py` on 2026-11-19: the game holds the foreground for 0.000 s (before: about 2 s per start, or 10 ms with the old injected hand-back). `focusguard.py` remains as a safety net: it only watches, and if a window of the game is in the foreground it writes the handle of the previous window into the hand-back slot (0x884F90); the game then calls SetForegroundWindow itself at its next frame. It logs each case in `focusguard.log` next to the tools folder: an empty log means the game never had the focus.
- The stock frame loop (0x472D40) idles when the window lost the focus (flag 0x5C4F94, cleared at 0x4728F2 - patch that immediate to 1) and the race pauses on focus loss (0x403652 `74 76` -> `EB 76`).
- Menu without keys: hook `call 0041F7B0` at 0x4149B2 to call the page setter 0x413DD0(state) on the game's own thread; replace the `call 0045C890` input reads (options page: back 0x41FB47, select 0x41FB70, left 0x41FD59, right 0x41FE15; mouse moved/x/y 0x411810, 0x411AA1, 0x411AB6) by stubs returning injected floats; selected item = [menu+0x148], menu = [[0x5E851C]+4]. Stub out 0x472CE0 when simulating the mouse - it moves the real cursor.
- Calling game functions: no code is injected. The test builds poll a command slot once per frame on the game's own thread (`prep_fps.py`, `command_slot`: 75 bytes at 0x593B00, reached from the frame loop's `call 0043ACC0` at 0x472ED7). The slot at 0x884F60 holds function address, ecx, number of stack arguments, six arguments and the result at +0x24; the game clears the address when it is done. `remote_test.Remote.call(func, ecx, args)` fills it with plain memory writes. An exe without the slot never answers and the call stops with a message.
- Race without keys: set GameParameters mode/class/track, then `Remote.start_race()` (0x4122E0 with ecx = menu); player inputs via stubs replacing `call 0x45C890` at 0x43AE11/0x43AEA0/0x43AF29; skip the intro by NOPing 0x407081.
- Forced finish: write three lap times and lap counter 3 to car+0x258, but only after the car has been in state 2 ([car+0x2D0], after the green light) for a moment - written earlier, the values are reset and nothing happens. The result pages then need "menu select": stub the six reads in fn 0x421970 (0x4219E3, 0x421A8B, 0x421BDB, 0x421C4F, 0x421CA5, 0x4222CA) with a one-shot float, write the selection to [menu+0x148] right before each press (the menu clears it while the real mouse moves), menu = [[[0x5E851C]+4]+0x144] during a race.
- Several test games at once (since 2026-11-22): every start goes through `gameslot.spawn` (optest.launch/start call it). Rules: one game per game folder (lock file `.claim.lock`, released by Windows when the process ends; also waits while an orphaned game runs from the folder); nothing starts while the user's real game runs (a game process that holds the single-instance lock and runs from outside `.claude\sandbox` / `.claude\worktrees` / Temp\claude); test builds without the lock (all prep_fps.build builds, see `pu_noinst.py`) run side by side up to `MHK2_MAX_GAMES` (default 3, counted over the whole PC); a build that still has the lock runs alone after 40 s without any game; one start at a time PC-wide (named mutex `Local\mhk2-sandbox-launch`, held until the menu). Games are recognised by the bytes at 0x46F3AC in their memory, not by name. ghosttest/classtest pick the first free folder of game, game2, game3 (`MHK2_GAME` forces one); extra folders are filled from game\ (missing files only; Phantom and settings.dat from the fixtures), setup_sandbox.py updates them. The pid file is `<game folder>\game.pid`. Each game keeps one CPU core busy (32 logical here). Straight runs next to another game gave the same results as alone within the run-to-run noise (end x within 0.6 mm, 2026-11-22, runs\parallel). `parallel_check.py` tests it all. Full check as a job queue (2026-11-22): `jobs.py <name> [selector]` splits every scenario, race set and straight run into its own job, three workers in game/game2/game3, longest job first by `runs\jobtimes.json`; all 49 jobs 12.3 min (run_checks serial was about 40, three fixed groups 15), classtest alone 4.0 min instead of about 12; results identical to the serial runs (runs\q1, runs\par1 vs runs23). See [[mhk2-powerups-and-class-factors]] for the lock itself.
- Windows Defender (2026-11-18, 23:19): real-time protection quarantined `tools/__pycache__/focusguard.cpython-312.pyc` in the scratch folder as "Exploit:Python/Leivion.C" (severe), scanned when `du` read the folder right after it had been moved. The match was on the technique: the old `focusguard.py` and `remote_test.py` opened the test game's process, allocated executable memory, wrote a stub and started it with CreateRemoteThread. The user saw the alert and asked about it. Nothing in the repository or the game folders was flagged. Since 2026-11-19 no helper does that any more (see the two points above): they only read and write plain values in the game's memory. Never change Defender settings, add exclusions or restore quarantined files: that is the user's decision. Do not bring VirtualAllocEx / CreateRemoteThread back into a helper.
- Screenshots: BitBlt from GetDC(hwnd) works even when the window is covered. Do NOT use PrintWindow - it stalls the game's frame loop.

Useful addresses: GameParameters* at [0x5E84EC] (class +0x10, unlocked class +0xFD08, unlock mask +0xFD0C), CarManager* at [0x5E8520] (car pointers at +0x10..+0x14, race time +0x20; car lap times +0x258, lap counter +0x264 - writing 3 laps forces a finish).

Tooling gotcha: Bash-tool heredocs collapse `\\` to `\`, which corrupted a generated Python file with byte escapes - write such scripts with the Write tool.

Trap, found 2026-11-19: the game writes `settings.dat` when a race starts. Whatever a test wrote into GameParameters before that (tuning values, the marker of the 60 FPS physics switch, class, unlock state) is in the sandbox's `settings.dat` afterwards, and the next run starts with it. A batch of 200 FPS races "with the switch off" had it on that way, inherited from a run with `--physics60`. `ai_race.py` therefore writes the switch on every run, on or off; `ghosttest.restore()` puts the pristine `settings.dat` and phantom folder back, and the test scenarios call it first.

Stopping a batch: a background shell script that is stopped from outside can leave its `sh.exe` running, which then starts the next test game. Give a batch a stop file it checks between runs (`touch <out dir>/stop`), or stop the `sh.exe` processes first, then the Python and game processes it started.

**Why:** exclusive fullscreen rearranges the user's desktop, and focus/keyboard/cursor grabs interrupt their work.
**How to apply:** use this recipe whenever a change to `tools/patch_200cc.py` needs a live check. The patcher needs the ORIGINAL exe (sha256 starts 272bfad5...), named as `original_exe` in `.claude/sandbox/local.json` (not in git; see `paths.py`); a game folder the patch was installed into holds a patched exe - verify by hash. The sandbox is `.claude/sandbox/` in the repo (since 2026-11-19; before that a temp folder): scripts in `tools/`, the game copy with the test builds in `game/`, original exe and disassembly in `work/`; `py .claude\sandbox\tools\setup_sandbox.py` rebuilds it, `.claude/README.md` has the details. `ghostlib.py` / `ghosttest.py` are the drivers for the phantom karts, `prep_class5.py` / `classtest.py` those for the engine classes and the tuning page (see [[mhk2-engine-classes]]), `pu_run.py` / `hold_speed.py` those for top speeds (see [[mhk2-powerups-and-class-factors]]). See also [[mhk2-user-context]] and [[mhk2-fps-physics-root-cause]].
